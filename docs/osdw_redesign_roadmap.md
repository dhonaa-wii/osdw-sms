# OSDW SMS — Visual Redesign Roadmap

Tracks the phased redesign that brought the UI up from the original functional-but-flat build to a professional, consistent design system. Started from the landing page, then rolled the same visual language out screen by screen. Each phase ends with a visual check (desktop + mobile) and a full test-suite run before moving on.

Read this alongside `docs/osdw_development_guide.md` (design system tokens, conventions) — this file tracks *progress*, not policy.

## Design language established

- **Icons**: hand-authored inline SVG, 24×24 viewBox (or scaled down), 1.5–2px stroke, round caps — no icon library. Established on the landing page's "Good to know" section, reused everywhere since.
- **Status stamps**: left border-rule + small uppercase tracked label, never color alone. Centralized in `App\Enums\ApplicationStatus::stampClasses()` + `<x-ui.status-stamp :status="..." />` (see below) — don't reintroduce inline `match()` blocks for this.
- **Motion**: one-shot only (scroll-reveal, count-up, card hover-lift). Never on content inside a Livewire-reactive region (`wire:model.live`, frequent `wire:click` re-renders) — morphdom strips JS-added classes on re-render, silently breaking the animation. Confirmed safe on static/mount-once pages only.
- **Quick links**: added only at genuine dead-ends (empty states, post-submit confirmation, cross-flow returns like "Already applied? Track your application"). Not on every page — see the cross-cutting principle from the Phase B planning note.
- **Charts**: hand-rolled SVG/CSS bars, no charting library. Established on the staff/head/admin dashboards.

## What's done

**Landing page** — hero with a live reference-tracking mock, animated stats, connected stepper, enriched offering cards, icon-led "Good to know" list.

**Phase A (shared components)** — `x-ui.back-link` (real SVG arrow, hover nudge — was a raw `&larr;` entity), `x-ui.empty-state` (default icon), `x-ui.modal` (entrance animation), `x-ui.data-table` (icon sort arrows), `x-ui.button` (transition polish), `x-app.sidebar` (hover/active transitions).

**Phase B (public pages)** — browse, show, track-lookup, track-dashboard, apply, track-recover, results, interview-schedule. All redesigned with consistent card/icon treatment and the quick-link principle applied at real dead-ends only.

**Dashboards** — staff/head dashboard got iconized funnel stats (with the one legitimate use of the gold accent color, on "Awarded"), real progress bars for slot/budget/term utilization. Admin dashboard was a placeholder sentence before this — now real iconized summary cards (colleges, programs, providers, funding sources, scholarship programs, academic terms, user accounts), each linking to its management page.

**Phase C, first slice (staff applicant review)** — `staff.applications.index`, `.workspace` (queue + shortlist tabs, slot counter with icon + bar), `.review` (screening checklist with SVG check/✕ icons instead of raw glyphs, status stamp). Introduced `x-ui.status-stamp` and retrofitted `track-dashboard.blade.php` to use it too, removing 3 copies of the same `match()` block.

**Phase C, second slice (staff interviews)** — `staff.interviews.sessions` (panelist rows rebuilt on `x-ui.input`/`x-ui.select` instead of raw unlabeled controls, with an accessible SVG trash-icon remove button), `.session` (new icon-led "Assigned" capacity stat card reusing the workspace slot-counter pattern, sat next to the existing "Panel" card), `.scoring` (rubric card matching review.blade's document-rubric layout — weight/max shown per criterion, right-aligned mono score input). `score-sheet.blade.php` (the print view) was left untouched — it's a standalone print document outside the app shell, not part of this design system.

**Phase C, third slice (awards, announcements, reports, audit-log)** — Added `stampClasses()` to `AwardStatus`, `AcceptanceStatus`, `ComplianceStatus`, and `AuditAction` (same match-expression pattern as `ApplicationStatus`), so all four now render through `<x-ui.status-stamp>` instead of ad hoc inline color spans. `awards.workspace`: gold icon-badge slot counters (gold, not forest — this is the one workspace where the award/gold association is earned, matching the design doc's "gold appears only at the moment of award" rule), icon-led out-of-rank/conflict warning rows, raw `<textarea>`s swapped for `x-ui.textarea`, awarded-list rows now show all three award statuses as stamps side by side. `announcements.index`: megaphone icon badge per row, published/draft as a stamp instead of inline text. `reports.index`: icon badges on every card title, scholars-per-college/per-funding-source converted from plain text rows to bar rows (bar width relative to the max amount in that list), application funnel rebuilt as a proper funnel bar chart (each stage's bar width relative to "Received"), retention converted to two icon stat tiles, multiple-award holders and disqualification reasons converted to icon-led list rows matching the dashboard's "Pending tasks" pattern. `audit-log.index`: action column now a status stamp (created/approved = forest, updated = azure, overridden = amber, deleted = crimson), added the missing `hover:bg-paper` row-hover treatment other data tables already had.

- **Second Blade `@foreach`-with-inline-array landmine (fixed)**: writing `@foreach ([['label' => ..., 'value' => ...], ...] as $stage)` directly in a template — a literal array of arrays inline in the directive — broke Blade's compiler with `syntax error, unexpected token "endforeach"`. Blade's directive-arg extraction gets confused by the nested brackets, similar in spirit to the already-documented Pint/Livewire-SFC landmine above but a different mechanism (Blade compiler, not Pint). Fix: never write a multi-element array literal inline inside `@foreach(...)` — build it in a preceding `@php ... @endphp` block and loop over the variable instead. Caught immediately by the test suite (`ReportsTest` failed with the raw PHP syntax error), not by visual QA — worth remembering that Blade compile errors like this only surface once a request actually renders the view, so a passing `pint`/static check won't catch them.
- Verified this slice end-to-end with a real browser (Playwright, installed ad hoc — no `chromium-cli` or existing browser driver in this Windows/XAMPP setup) against `DemoDataSeeder` data: logged in as OSDW Head, screenshotted all four pages at 1280px and 375px, and additionally drove a real award + forfeit action to populate the audit log so the action-stamp colors could be confirmed against real "created"/"updated" rows rather than just the empty state. No console errors, no layout breakage at either width.

**Phase D (admin: master data + program configuration)** — Deliberately restrained per this phase's own framing: dense CRUD tables, not motion-heavy. No icons were added to page headers or table rows (that's not the established pattern for list/index pages anywhere else in the app — icons stay on dashboard-style stat tiles and card grids). What changed:

- New `x-ui.active-stamp` component (`:active="$model->is_active"`) replacing four duplicated inline Active/Inactive `<span>` blocks across `colleges`, `programs`, `providers`, `scholarship-programs`, and `user-management` — same anti-duplication rationale as `x-ui.status-stamp`.
- Added `stampClasses()` to `OfferingStatus` and `EmailStatus` (removing an inline `$statusStyles` match array in `offerings.blade.php` and an inline if/elseif chain in `email-log/index.blade.php` — both were the exact pattern this roadmap already says not to reintroduce).
- Added the missing `hover:bg-paper` row-hover transition to every master-data and program-configuration data table — present on all the Phase C tables but never carried over to admin's.
- **Settings hub redesign** (`admin/settings/index.blade.php`) — was plain bordered link-cards with no icons; rebuilt with the same icon-badge treatment as the admin dashboard's card grid (the two pages are structurally identical — a grid of link cards — so they should look identical). More importantly, it was missing links to **Providers, Funding Sources, and Scholarship Programs** entirely — three fully-built admin screens with no path to them from the settings hub. Added all three. Extended `SettingsIndexTest` to assert on them, since the existing test's name ("sees links to every low frequency setting") implied coverage it didn't actually have.
- **Navigation-consistency fix**: `funding-sources`, `providers`, `user-management`, and `email-log` were missing the `x-ui.back-link` to Application Settings that every sibling admin screen has. Added it to all four.
- **Second mobile-only layout bug (fixed)** — same root cause as the panelist-row bug from Phase C, found in two more places: the form-field builder row (`offering-configuration.blade.php`: Label input + Type/Stage selects) and the offering-college row (`offerings.blade.php`: College select + Slots input + Remove). Both used a non-wrapping `flex gap-3` row with fixed-width children; at 375px the Label input was squeezed down to a handful of pixels and rendered its value truncated to a single character. Same fix as before: `flex-col sm:flex-row` on the row, fixed widths become `w-full sm:w-*`, and for the offering-college row a nested `flex` group keeps Slots+Remove paired when stacked. This is now a three-strikes pattern — **any dynamic-array form row with a flex-1 text input next to fixed-width siblings needs this treatment by default, not just when a bug report comes in.**
- Verified all 13 admin screens end-to-end with Playwright (admin login, 1280px + 375px, no console errors) before and after the mobile fix.

**Phase E (login, error pages, full click-through)**:

- **Logout redirect** — changed from `route('login')` to `route('home')`. Landing on the login page after signing out reads as "you're still half-logged-in, do it again"; landing on the public homepage reads as "you're back to being a visitor," which is what actually happened. Updated `StaffAuthTest::test_logout_ends_session` to match.
- **Login page rebuilt** on `x-ui.input`/`x-ui.button` — it was the one form left in the entire app using raw `<input>`/`<label>`/`<button>` markup instead of the shared components, so it had its own hand-rolled (but slightly different) focus-ring and error-message styling. No behavior change, pure markup consolidation.
- **New custom error pages** (404, 403, 419, 500) — none existed before this; all four fell back to Laravel's stock error pages. Built a shared `x-errors.page` component (full standalone HTML document — deliberately *not* reusing `layouts::public`, since that's wired for Livewire's layout mechanism via `#[Layout(...)]` and these are plain Blade views that need to render even if the app shell itself is what's broken) plus one view per status code. Each has a status-appropriate icon, the code in JetBrains Mono (a deliberate small echo of the reference-number treatment — these are also numbers a user might read off screen), and an instructive rather than apologetic message per the writing guidelines. The 403 page conditionally links to "Go to your dashboard" for authenticated users or "Return to homepage" for guests — genuinely different next actions, not a cosmetic split. Covered with `tests/Feature/ErrorPagesTest.php`: 404 and 403 verified via real HTTP requests (both are `HttpException`s Laravel renders through the custom view regardless of `APP_DEBUG`), 419 and 500 verified by rendering the view directly (419 needs a real CSRF mismatch to trigger naturally and 500-in-debug-mode shows Ignition instead of the custom view, so a direct render is the reliable check for both).
- **Full click-through QA** — staff and admin screens were already thoroughly covered by the Phase C/D visual passes, so this phase's actual new ground was the public/student-facing flow, which had never been checked with a live browser in this project: landing, browse, show, apply, track-lookup, track-recover, results, interview-schedule. All eight load clean with zero console/HTTP errors. Also re-verified logout lands on the homepage for both OSDW Head and Admin.
- **QA methodology note, not a bug**: a full-page screenshot of the landing page initially looked broken — "Open right now" and "Announcements" rendered as empty gaps. This is the documented one-shot `data-reveal`/`data-reveal-group` scroll animation working exactly as designed: content starts at `opacity: 0` and is revealed via `IntersectionObserver` as it scrolls into view, and a single full-page screenshot never scrolls anything into view, so below-the-fold reveals never fire. Confirmed by re-screenshotting with Playwright's `reducedMotion: 'reduce'` context option, which the app already respects (`@media (prefers-reduced-motion: reduce)` in `app.css` skips the animation entirely) — content appeared immediately. **Any future full-page screenshot QA on a page using `data-reveal` needs `reducedMotion: 'reduce'` emulated first**, or it will produce false "missing content" findings below the fold.

## Fixes discovered along the way

- **Pint landmine (fixed permanently)**: Pint's `array_syntax` fixer was rewriting `array('title' => ...)` to `['title' => ...]` inside every `#[Layout(...)]` attribute, and the nested `]` breaks Livewire's SFC-detection regex — 500s the page. Hit this on 10+ files across two sessions before adding `pint.json` with `array_syntax: false`. Confirmed fixed — Pint no longer touches these lines.
- **`ScreeningService` stage bug (worked around, not fixed, now moot)**: `recordCompletenessChecks()` checked *all* required `OfferingFormField`s regardless of `stage`, so a required `post_award` field incorrectly blocked *pre-application* screening. Only surfaced because the demo seeder added a post-award field — the base seeder never had one. Worked around in the seeder by not marking that field required. Resolved as a side effect of removing the post-award compliance stage entirely (post-award requirements don't exist anymore — compliance is established at screening, per `CLAUDE.md` rule 4) — `offering_form_fields.stage` and the `RequirementStage` enum were dropped, so the bug's precondition no longer exists.
- **Dashboard "Trends across terms"** was showing `₱0.00` for terms with zero awards — now conditional on `awardedAmount > 0`.
- **Not a bug**: `workspace.blade.php`'s tab switcher uses Alpine (`x-data`/`x-show`/`@click`). Alpine isn't a separate dependency — Livewire bundles and auto-starts its own instance (`window.Alpine`). Confirmed working; no action needed.
- **Stale CSS build after introducing a new-to-the-codebase Tailwind utility**: `sr-only` was used for the first time on the interviews slice (accessible label on the panelist remove button and the attendance-status select). Tailwind's JIT scan only regenerates what's referenced in the last build, so the class silently rendered as visible text until `npm run build` ran again. There's no watcher running alongside `php artisan serve` in this setup — **run `npm run build` after adding any Tailwind utility class that hasn't appeared elsewhere in the codebase before checking it in a browser**, not just after JS/CSS source edits.
- **Mobile-only layout bug (fixed)**: the panelist form row (`sessions.blade.php`) used a single non-wrapping `flex` row for Name input + Role select + remove button. Fine at desktop width, but at 375px the three controls compressed into an unreadable strip. Fixed with `flex-col sm:flex-row` on the row and a nested `flex` group for Role+remove so they stay paired when stacked. Caught only by screenshotting at the mobile breakpoint — worth doing for any new dynamic-array form row, not just static layouts.

## Out-of-phase fixes (2026-08-09)

Three gaps surfaced while reviewing the interview screens, outside the phase-by-phase visual sweep:

- **Staff document viewer** — `review.blade.php`'s Documents card showed filename + status only; staff had no way to see the actual uploaded file before verifying/rejecting it (works against the "staff verify against uploaded documents" rule in CLAUDE.md). Added `GET /staff/applications/documents/{document}` (`staff.applications.documents.show`), streamed via `Storage::disk('local')->response()` — same pattern as the existing `database-backup.download` closure route. Added a "View" link (eye icon) next to each document row, opens in a new tab.
- **Modern applicant upload** — all three applicant file-upload spots (`apply.blade.php`, and twice in `track-dashboard.blade.php`) were a bare `<input type="file">`. Built `x-ui.file-upload`: Alpine-driven drag-and-drop dropzone, filename/size preview, real progress bar via Livewire's `$wire.upload()` JS API (not `wire:model` — cleaner for a hand-rolled dropzone, same underlying upload mechanism so no server-side changes needed). Verified end-to-end with Playwright's `setInputFiles` — confirmed a real `POST /livewire-*/upload-file` fires and the preview updates.
- **Dead sidebar nav** — "Sessions & Scheduling", "Award Processing", "Scholar Monitoring" rendered as plain `<li>` text, not links; their target pages exist but need an `{offering}` param with no offering-agnostic entry point. Renamed `staff.awards.index`/`staff.scholars.index` → `.workspace` (freeing `.index` for a new picker, matching the existing `applications.index`/`applications.workspace` convention) and added three picker pages (`staff/interviews/index.blade.php`, `staff/awards/index.blade.php`, `staff/scholars/index.blade.php`) modeled on `applications/index.blade.php`. Removed the "Executive Dashboard" placeholder entirely — its content (budget/slot utilization, term trends) already renders on the main Dashboard for the Head role; it was redundant, not unbuilt.
- **Scholar Monitoring redesign** (user-requested mid-flow, referencing the real SUC-Levelling spreadsheet as the density bar to hit) — converted the scholars roster from one card per student to a dense `x-ui.data-table` (Student / Status / GWA / Units / Retention / Actions). The per-scholar status-setting form (reason + Active/Probation/Graduated/Terminate buttons) and full retention-rule breakdown moved into an `x-ui.modal`, opened via a "Review" action — keeps the table scannable while still surfacing full detail before a status decision.

Added feature test coverage for all of the above (document viewer auth + streaming, each new picker page, the `awards.workspace`/`scholars.workspace` rename) rather than relying on existing tests alone.

## Out-of-phase changes (2026-09-22)

**Awards simplified to screening-and-recording only** — the system does not process award distribution. Removed: the accept/decline step (`AwardService::accept()`/`decline()`, `AcceptanceStatus` enum, the public tracker's accept/decline buttons), forfeiture (`AwardService::forfeit()`), and the `scholar_terms` renewal/GWA/retention-evaluation engine (`ScholarTerm` model, `ScholarTermStatus` enum, `RetentionService`). The separate `staff.awards.*` module (`awards.workspace`, added in the "Out-of-phase fixes (2026-08-09)" entry above) was redundant with `applications.workspace`'s own Shortlist-tab "Award" action and was deleted outright — awarding happens from the Shortlist tab in one immediate, final step, gated by slot limits and outstanding additional requirements. `staff.scholars.workspace` (Scholar Monitoring) is now a read-only roster built directly off `awards`, replacing the GWA/retention-modal version described in that same entry. Sidebar lost its "Award Processing" item as a result. `ApplicationStatus::Approved`/`Accepted`/`Forfeited` collapsed to a single `Awarded` case; `AwardStatus` and `AcceptanceStatus` were deleted along with the `awards.status`/`acceptance_status`/`accepted_at` columns. `offering_retention_rules` configuration remains unused by any consumer now — the table is kept as-is in case a future retention feature is built, but nothing evaluates it today.

## Out-of-phase changes (2026-09-27)

**Program-level requirements template removed** — the program no longer holds a requirements template that offerings copy from. Dropped `program_form_fields`, `program_eligibility_rules`, `program_retention_rules` and their models; `ScholarshipProgram` is now identity-only (name, provider, description). `OfferingService::openOffering()` no longer copies anything into the new offering — every offering starts blank and staff configure its form fields, eligibility rules and retention rules directly, from the offering's own Requirements page. The program-level Requirements page (`program-configuration.blade.php`, route `admin.scholarship-programs.configure`) and the "Requirements"/"Set requirements" links pointing to it were removed.

**Type of scholarship moved from program to offering** — `category` (`App\Enums\ScholarshipCategory`) is dropped from `scholarship_programs` and added to `program_offerings`, following the same precedent as `college_scope` and `allocation_mode`. It's now set when an offering is opened, not fixed for the program's lifetime. `ConfiguresApplicationForm::isAcademic()` reads it off the offering's own `configurationOwner()` instead of a separate `owningProgram()` lookup, which was removed. The SUC-Levelling report's Type column now sources from `program_offerings.category`.

**Additional requirements removed** — the Shortlist tab's "Set additional requirements" feature is gone: the `offering_additional_requirements` and `application_additional_requirements` tables (dropped by `2026_09_27_000007_drop_additional_requirement_tables`), `AdditionalRequirementService`, the `RequirementSubmission` enum, both models, the staff receipt-download route, the per-applicant tick column, and the "Documents needed" upload block on the applicant's tracking page. `AwardService::create()` is now gated by slot limits only. Every requirement is checked during screening; nothing is asked for after shortlisting.

## Next up

Phases C, D, and E are complete — the full phased redesign sweep is done. Nothing formally scheduled next; treat any further visual work as targeted fixes rather than a new phase.

**Standard requirements** — the admin keeps one standard application form and one set of standard disbursement requirements (`standard_form_fields`, `standard_requirements`, page `admin.scholarship-programs.standard-requirements` opened from Scholarship programs). An offering's Requirements page chooses "Standard requirements" or "Set manually" (`program_offerings.requirements_source`, default manual). `StandardRequirementService` copies them into the offering's own rows and keeps them in step until the first application. The requirement modal moved into `<x-config.requirement-dialog>`, and `ConfiguresApplicationForm` now reads fields through `formFieldsQuery()` so it also drives the standard form.
