# OSDW Scholarship Management System

A web-based scholarship application and management system with departmental classification, built for the Office of Student Development and Welfare (OSDW) of a Philippine state university. This is an undergraduate capstone project.

## Reference documents

Read these before implementing anything. They are the source of truth — if this file and a doc disagree, ask me rather than guessing.

- `docs/osdw_scholarship_system_schema.md` — database schema
- `docs/osdw_modules_and_features_per_user.md` — features per user role
- `docs/osdw_development_guide.md` — conventions, design system, build order

## Stack

- Laravel 12 (PHP 8.2+)
- Livewire 4 — **not** Livewire 3. Use Single-File Components, `Route::livewire()`, and `#[Validate]` attributes. Do not follow v3 patterns with separate class and view files.
- Tailwind CSS 4 — theme tokens live in `resources/css/app.css` under `@theme`. There is no `tailwind.config.js`.
- MySQL 8 via XAMPP
- Alpine.js for small client-side interactions only

## Domain context

**Users:** Students/applicants (student accounts, `UserRole::Student`), OSDW Staff, System Administrator. There is no OSDW Head role and no panelist role — the Administrator absorbs everything Staff can do plus final award approval and full audit-log/executive-dashboard access. All three log in from one `/login` (`auth::login`) and land on `User::homeRoute()` — My applications for students, the dashboard for staff.

**Student accounts.** An account is tied to one email. Registering (`auth::register`) mails a 6-digit OTP (`OtpService`, `email_otps`, `OtpPurpose`) that must be entered before the account exists; the password is the system's own, not the email's. "Continue with Google" (Socialite, `GoogleAuthController` → `AccountService::signInWithGoogle()`) skips the OTP and shows only when `GOOGLE_CLIENT_ID` is set. A forgotten password is reset with an emailed OTP (`auth::forgot-password`). Right after registering, the student sets up their profile once (`student::complete-profile`): the Student ID — unique system-wide, never editable afterwards — plus personal details, which become their `applicants` row (`applicants.user_id`). The `student.profile` middleware sends a student without one there. Settings (`student::settings`) edits the personal details and password only. Browsing (`programs.index`, `programs.show`) is public but lists only `ProgramOffering::open()` offerings — closed and upcoming ones are 404 publicly. `programs.apply` needs a student account (guests go to log in, then back). A student sees only their own records: My applications (`student.applications.index`, filtered by `StudentApplicationFilter` groups: in progress / awarded / not approved) and the application page (`student.applications.show`, `Application::isOwnedBy()`), which is the old tracking page plus the submitted form read-only and the offering's announcements. There is no search over applicants anywhere on the student side. Published results list consenting awardees and count the rest ("N more awardees chose not to have their names published").

**Student notifications.** A bell (`student::notification-bell`, in both public layouts) backed by Laravel database notifications (`StudentNotification`, `NotificationKind`), filled by `StudentNotificationService`: status changes (from `ApplicationStatusLog::created` — the student's own submit/auto-screen is skipped), requirement stages opened, interview scheduled or moved (shortlisted applicants only), offering and general announcements (first publish only; general ones go to every student and show on the landing page), results published (first publish), award disbursed (`StudentNotificationService::disbursed()`, sent from `AwardService` since disbursing writes no status log), and registration opened / closed for every offering that takes new applicants — to every student, once each (`registration_opened_notified_at` / `registration_closed_notified_at` claimed with a guarded update). Closing counts the deadline and the application cap. Those registration notices are sent by `syncRegistrationNotices()`, run every minute by the scheduler (`osdw:registration-notices`), after every submission, and on each bell render, so they go out without a scheduler too. Existing emails (award, renewal, incomplete) are still sent and link to the application page.

**Staff accounts.** Only the administrator makes them (Users page, `admin.users`): name and email; the system generates a temporary password (`AccountService::createStaff()`), shown to the admin once in the notice modal. "Reset password" generates a new one the same way (`resetStaffPassword()`). An OSDW Staff account whose `users.password_changed_at` is null — or, when `GOOGLE_CLIENT_ID` is set, that has no `google_id` — is sent by the `staff.setup` middleware (`User::needsAccountSetup()`) to the first-login page (`staff::account-setup`, `staff.account.setup`): set their own password, then connect a Google account (`auth.google.link` → the same Google callback, which links instead of signing in when someone is signed in; `AccountService::linkGoogle()` refuses a Google account whose ID or email belongs to another account). The Users list stamps such accounts "Setup pending". Administrators skip setup. Staff and admin have a Profile page (`staff::profile`, `staff.profile`): edit their name, change their password, and connect or switch their Google account; the email is changed only by the admin.

**Staff notifications.** The staff layout has a top bar with a bell (`staff::notification-bell`) and an account menu (Notifications, Profile, Log out), built like the student header; the shared item is `<x-ui.notification-item>`. `StaffNotificationService` sends `StaffNotification`s to every active staff and admin account for exactly four events: a new scholarship program created (admin opens its offerings, staff the Applications list), an offering opening and closing for registration (from `syncRegistrationNotices()`, same once-each claim as the students'), and the interview scheduled or moved (`OfferingRequirementService::saveInterview()`). The last three open the offering's workspace; the full list is `staff.notifications`. Don't add other staff notification events without asking.

**Key constraints:**
- No integration with the school's student information system. Students self-encode their data; staff verify against uploaded documents.
- Single campus.
- OSDW staff review all applicants — there are no per-college coordinators.
- Awards and their disbursement are recorded, not processed. No payment processing.

**Critical business rules:**
1. `student_id` is the global identity key. The same student across programs and terms is one `applicants` record.
2. Students may apply to multiple programs. Do not block this — flag it. When reviewing, staff must see the applicant's other applications and awards ("Scholarships held" card, `<x-staff.scholarships-held>`; "Grantee elsewhere" / "National grantee" flags on the queue and shortlist). The one exception is the **one-national rule** (`ScholarshipHoldingService`): a student holding a scholarship whose provider's funding source is national (`FundingSource::isNational()` — National Government or National Non-Government) can't apply to another national scholarship (`applyBlocker()`, checked in `ApplicationService::submit()`, the Apply page and the scholarship page, which shows the reason instead of Apply now) but can apply to local ones; a local grantee can apply to anything. A student may apply to two national scholarships at once, but once one is awarded the other can't be endorsed or awarded (`awardBlocker()`, enforced in `AwardService::create()`), and their application page says so. "Holds" means their latest award in a program chain, unless a later renewal in that chain was denied. In-house, Academic and Non-academic sources are not limited.
3. The system screens for eligibility and completeness. It does **not** score, rank, or decide. Staff manually shortlist or reject each application, then award directly from the shortlist within slot limits. The one exception: an **academic** offering's required GWA (set on its Requirements page) is a hard gate — an application below it cannot be submitted (`EligibilityService::unmetGwaRule()`). Likewise an offering's **family income cap** ("Maximum family monthly income" on the offering form, blank = no cap, stored as an `income` / `lte` eligibility rule) refuses an application above it (`unmetIncomeRule()`) — family monthly income is a system field asked on every application, and the cap itself is never shown to students; other failed eligibility rules are only recorded for staff. (Ranking by GWA and family income is a planned future feature, not built yet — don't reintroduce scoring or rank-based ordering without asking.)
4. Requirements come in three places, all configured on the offering's Requirements page (`admin.offerings.configure`) — a renewal offering's page holds only its renewal requirements instead (see 4b): the **application form** (checked during screening, before endorsing), **additional requirements**, and the **interview**. Each additional requirement is tied to a stage (`RequirementStage`): `shortlist` requirements must all be complied before the applicant can be awarded (`AwardService::create()` enforces it); `award` requirements are asked of awardees afterwards for the award release and never block anything. Each is submitted as an upload, a physical copy, or both (`SubmissionMode`), and can carry an optional blank form (e.g. a contract) that admin uploads and applicants download from their application page; staff verify them on the review page, and applicants see them and upload on their application page. Applicants see only the application form while applying; each later stage is opened by staff (`ProgramOffering::hasOpenedRequirements()`, gating `OfferingRequirementService::activeStages()`): "Open shortlist requirements" on the Shortlist tab (`shortlist_requirements_opened_at`, enabled once shortlisted + awarded new applicants reach `total_slots` — the shortlist may exceed the slots) and "Open disbursement requirements" on the Grantees page (`award_requirements_opened_at`, enabled once every slot is awarded). Both are one-way. The interview is one schedule per offering (date, venue, instructions), shown on the Shortlist tab (with a "Schedule interview" link to the Requirements page for administrators) and on every shortlisted applicant's application page — no per-applicant slots, no publish step. There is no accept/decline step: awarding is a single, immediate, final action staff take from the shortlist. Don't reintroduce an acceptance or compliance-confirmation step without asking.
4a. The system only screens and records. It does not process award distribution. The **Grantees** page (`staff.grantees.index`) is a roster of recorded awards — one row per grantee per offering group at their latest award, the scholarship shown as program · offering name, search by name or student ID, a program → offering-group filter whose chain tabs open on the latest offering, once filtered to an offering that takes new applicants, "Publish results" (public awardee page per offering: instructions, then a compact table; the public Published results page lists published offerings, not awardees) and "Open disbursement requirements", both enabled only when every slot is awarded, and "Disburse all", enabled only when every slot is awarded and every grantee in the offering has every disbursement requirement complied (uploads verified, physical copies received) (`AwardService::disburseAll()`), a "Disbursement requirements" count (or a "Disbursed" stamp once disbursed) that opens a modal where staff and admin verify, return or mark received the award-stage requirements, and a "View" link to the grantee page (`staff.grantees.show`: student information, then each application and renewal in the group with its form, documents and requirements, and a "Disburse" button on each award, enabled once its disbursement requirements are all complied — renewals need none) — nothing more. Disbursing only records it: `awards.disbursed_at` / `disbursed_by` are set, one-way; the application stays `awarded` and its status label reads "Disbursed" (`Application::isDisbursed()`), with a "Disbursed" entry at the end of both status timelines. Award-stage (disbursement) uploads, like renewal ones, are submitted once and can be uploaded again only after staff return them (`RequirementStage::isSubmittedOnce()`). Don't reintroduce accept/decline, forfeiture, or a `scholar_terms`-style monitoring table without asking.
4b. **Renewal.** Every scholar still enrolled renews — there are no renewal slots and no grade standards; staff judge from the documents. A **renewal offering** is an offering with `renews_offering_id` set: it continues one earlier offering of the same program and takes that offering's awardees — by default no slots, no public application form, not in `ProgramOffering::open()`. With "Open to new applicants" (`accepts_new_applicants`) it also takes new applicants like a first offering (`ProgramOffering::takesNewApplicants()`): slots for new applicants only, application form, shortlist/award requirements and interview on its Requirements page next to the renewal requirements, and a "New applications" tab first on its Renewals page that opens its queue/shortlist workspace. The form suggests those slots as the scholars of the renewed offering in their last term — year level 4+ in a second-semester term (`RenewalService::graduatingCount()`); graduating scholars can still renew. Admin creates it with "Add renewal offering" on an offering's page, which links it to the latest offering in that group automatically (no cycle field, no picker). It keeps the type of scholarship of the offering it renews, and its dates are a submission window ("Submission starts" / "Submission due", in `opens_at` / `closes_at`) — renewal uploads are refused outside it. The admin offerings list and the staff Applications list show one row per group (the first offering); the admin offering page and the staff review pages (workspace, Renewals page) show the first offering and every renewal offering that continues it as tabs (`RenewalService::chainOf()`, `<x-staff.offering-chain-tabs>` — newest four, "View all" for the rest). For an administrator each offering's tab has a ⋮ menu with Edit and Delete (`DeletesOfferings` trait → `DeletionService::deleteOffering()`; only while it holds no applications and nothing renews it). A renewal offering's Requirements page configures only **renewal requirements** (`RequirementStage::Renewal`, upload / physical / both, optional blank form). A renewal is an `applications` row with `kind = renewal`. Admin runs "Open renewals" on the renewal offering's page (`RenewalService::openRenewals()`), creating one `screening` ("Under review") renewal for each awardee of the linked offering and emailing them. The scholar picks their year level this term (dropdown, submitted once; a renewal starts with none and can't be renewed until it's set) and hands in the renewal requirements on their application page — each upload once, view-only afterwards unless staff return it; staff open each scholar from the offering's **Renewals page** (`staff.renewals.index`, a list like the queue, not the queue/shortlist workspace) to their own **renewal review page** (`staff.renewals.review`), verify them there and renew (`AwardService::create()`, takes no slot, blocked until every renewal requirement is complied) or deny with a reason. Renewal offerings chain term after term until staff deny one (e.g. graduated) — there is no automatic graduation check.
5. A provider offers scholarship programs; a scholarship program runs in **offerings**, one per term, each named by the admin ("Batch 1"). The program is identity only — name, provider, description. It holds no requirements template: form fields, eligibility rules and requirements are configured directly on each offering, and opening an offering (`OfferingService::openOffering()`) starts it blank rather than copying anything. The one shared starting point is the admin's **standard requirements** (`admin.scholarship-programs.standard-requirements`, a button on Scholarship programs): one application form and one set of disbursement requirements — no shortlist requirements. On an offering's Requirements page the admin picks "Standard requirements" or "Set manually" (default, `requirements_source`). Standard copies them into the offering (`StandardRequirementService::useStandard()`, only before its first new application) and makes those two sections read-only; later edits to the standard requirements re-copy into Standard offerings until their first application, then the copy is frozen.
5a. **Deleting.** Admin can delete an offering (tab ⋮ menu or offerings list) or a whole scholarship program (Scholarship programs list) — soft deletes through `DeletionService`, allowed only while nothing in it holds applications or renewals; a program takes its offerings with it. Settings → Deleted items (`admin.settings.deleted-items`) restores them; after 60 days (`DeletionService::RETENTION_DAYS`) `osdw:purge-deleted` removes them for good. Records of real students are never deletable — don't relax the applications guard without asking.
6. Each offering's configuration is independent and editable. Editing one offering never affects a sibling offering. Everything that can change from term to term — name, type of scholarship (category), slots, dates, fund amount, college scope, eligible colleges, allocation mode, form fields, eligibility rules, additional and renewal requirements, and which offering it renews — lives on the offering only. Never hardcode one policy. There is only one award type: a cash fund amount, required on every offering. Tuition discount is not a supported award type — do not reintroduce a `discount_rate` field without asking.
7. The SUC-Levelling report is the system's headline output. Its column format is fixed by the agency — see section 8 of the schema doc. The **Reports** page (`staff.reports.index`) shows only this report. It uses the same filters and the same rows as the Grantees page (search, program → offering group with chain tabs, college — `ReportService::granteeQuery()`), and its Excel export downloads exactly the rows shown. "Print report" prints only the report — the same rows, loaded from `staff.reports.suc-levelling.print` (A4 landscape, OSDW header) into a hidden frame — without leaving the page. There is no term selector, date-range export, or summary cards (per college, per funding source, funnel, multiple-award, disqualification reasons); don't reintroduce them without asking.

## Conventions

| Thing | Convention |
|---|---|
| Table | plural snake_case — `offering_form_fields` |
| Model | singular StudlyCase — `OfferingFormField` |
| Controller | `ApplicationController`, grouped in `Public/`, `Staff/`, `Admin/` |
| Livewire component | kebab-case — `staff.applications.review-panel` |
| Route name | dot notation — `staff.applications.review` |
| Form request | `StoreApplicationRequest` |
| Enum | singular StudlyCase — `ApplicationStatus` |

**Business logic goes in `app/Services/`**, not controllers. `ScreeningService`, `AwardService`, `ReportService`. Controllers stay thin.

**Use PHP enums for all status and mode fields.** Never compare raw strings.

**Run `./vendor/bin/pint` before finishing any task.**

## Design system

Tokens are defined in `resources/css/app.css`. Use them as Tailwind utilities — never hardcode hex values.

- Text: `ink`, `slate`, `mist` · Surfaces: `paper`, `surface` · Lines: `line`
- Primary: `navy-600` / `navy-700` / `navy-900`
- Award states only: `gold-600`. Never decorative.
- Status: `amber-600` pending · `crimson-600` negative · `azure-600` informational

**Type:** Archivo for headings, Public Sans for body and forms, JetBrains Mono for student IDs, GWA, and amounts. The monospace choice is functional — these values get read aloud and typed by hand.

**Status stamps**, not pills: a left border rule plus a small tracked uppercase label. Uppercase appears nowhere else in the interface.

**Branding images live in the database.** The OSDW logo (landing hero, above "OSDW SMS" in the staff/admin sidebar) and the footer banner (landing footer) are rows in `branding_images`, served by `branding.show`. Get their URLs with `BrandingImage::url(BrandingImageKey::…)` — don't put them in `public/` or `storage/`.

**Public pages never show the award amount.** Browse, scholarship details, the application page and results show no ₱ figure; amounts appear only on staff/admin pages, reports and exports.

**Student pages feel like one app.** Public links use `wire:navigate` and component redirects `navigate: true`; saves confirm with a toast (`$this->dispatch('toast', message: …)`), not an alert pushed into the page; buttons pass `loading="…"` to `<x-ui.button>` so they keep their width while busy; search fields use `<x-ui.search>`. A redirect can carry a toast to the next page with `session()->flash('toast', …)`. The sign-in pages share `<x-auth.card>` (and `<x-auth.code-input>` for the OTP step); the student header has the bell and an account menu (Notifications, Settings, Log out).

**Staff/admin messages open in a modal.** Instead of an `<x-ui.alert>` pushed into the page, components call `$this->dispatch('notice', title: …, message: …, tone: 'success'|'error')`, which opens the shared `<x-ui.notice-modal>` in the staff layout. Form modals use `<x-ui.dialog show="$wire.showForm" close="$wire.showForm = false">`, whose visibility lives in Alpine, so they open on click with no round trip and a save never re-renders the page out from under the user (see `admin.offerings.configure`). Confirmations use `$store.confirm.ask({ title, message, confirmLabel, action: () => $wire.method() })` (the shared `<x-ui.confirm-modal>`), never `wire:confirm` or the browser's `confirm()`. Admin list pages and the staff Applications flow (Applications list, offering workspace, Renewals list) share one layout: a card with a toolbar (`<x-ui.search>`, `<x-ui.filter-select>`, `<x-ui.segmented>` switch with counts), `<x-ui.list-table>` compact rows that open on click, `<x-ui.icon-button>` row actions and `<x-ui.list-empty>`. The application and renewal review pages use the `<x-staff.review-*>` cards. No action result is ever an `<x-ui.alert>` — success and error both go to the notice modal; quiet row actions (verify, physical copy received) just update the row. Modals are compact (15px title, tight header and body).

**Uploaded files open inside the system.** Every link to an uploaded document (application documents, requirement uploads, blank forms) uses `<x-ui.document-link>`, which opens the shared `<x-ui.document-viewer>` modal placed in the staff and public layouts. Never link a file with `target="_blank"`. On staff/admin review pages (application review, renewal review, grantee page, disbursement modal) every student upload sits in one **Documents** card, grouped (`<x-staff.document-group>`) as Application documents, Additional requirements (the shortlist stage — `RequirementStage::reviewHeading()`), Disbursement requirements, or Renewal requirements, each shown in place with `<x-staff.document-item>` → `<x-ui.document-preview>`: name and status on top, Verify / Reject (Return for requirements) and Physical copy received beside it, then the whole file at full height (every page, no inner scrolling), so staff scroll the page from one document to the next. PDFs are drawn page by page with pdf.js (`window.renderPdfPreview` in `resources/js/app.js`, loaded on first use) so they work on phones; previews load as they scroll into view.

**Quality floor, always:** visible focus rings, real `<label>` on every input, error messages that say what to do, empty states that offer the next action, tables that collapse to cards under 768px, `wire:loading` states on every Livewire action.

**Interface copy:** buttons name the outcome ("Submit application", not "Submit"). Same word for the same action everywhere. Address students directly — "Your application is under review".

**No narration copy.** Never explain what changed, what used to be there, or how a field's value is computed — no "no longer set here", "now shown automatically", "this used to be manual", etc. That's a commit message, not interface copy; it belongs in this file or a PR description, not on the page. A hint on an input says what to type or what happens next in one short clause ("Leave blank for no cap") — it does not narrate the feature's history or restate the obvious. If a hint would just repeat the label or explain internal logic, cut it.

**No page subtitles.** A heading names the page; do not add a descriptive sentence under it restating or explaining what the page is for. If a heading needs disambiguating context (which offering, which term, which program), fold that identifier directly into the heading text instead of a separate line below it. This does not apply to error messages, empty-state next-action text, or validation hints on inputs — those stay, per the quality floor above.

## What not to do

- Do not use Livewire 3 syntax
- Do not create a `tailwind.config.js`
- Do not hardcode colors, statuses, or scholarship-specific rules
- Do not put business logic in controllers or Blade views
- Do not use `localStorage` or `sessionStorage`
- Do not add features that are not in `docs/osdw_modules_and_features_per_user.md`
- Do not invent domain policy. Slot rules and renewal requirements come from the agency — ask me.
- Do not build the payment, SMS, or SIAS integration modules. They are explicitly out of scope.
- Do not write narration copy in the UI ("no longer set here", "now automatic", "this used to be..."). See Interface copy rules above.
